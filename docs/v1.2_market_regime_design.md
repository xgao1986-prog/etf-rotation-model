> **代号**: Market Regime Enhancement  
> **目标**: 先建立可解释的市场状态检测框架，验证其对敞口配置的指导价值  
> **分支**: `feature/v1.2-market-regime`  
> **日期**: 2026-06-13  
> **状态**: 设计阶段（范围已收敛：v1.2 先做市场状态，不直接实现板块加成）

---

## 0. 范围决策

v1.2 的核心任务是把模型从“单纯 ETF 打分”升级为“先识别市场状态，再决定敞口结构”的框架。为避免一次性引入过多变量，v1.2 采用 **observer-first** 的方式：

1. 先实现市场状态检测模块，输出每日状态：强牛、弱牛、震荡、熊市。
2. 先在 CLI、UI、回测报告中展示状态，不立即让状态自动改交易参数。
3. 使用现有指数和 ETF 数据作为主要输入，优先验证状态识别是否合理。
4. 板块数据可以作为“市场宽度/结构性行情”的辅助观察指标预留接口，但不在 v1.2 中实现板块加分或板块切换交易。
5. 宽基和动态参数映射暂不进入默认交易逻辑，先作为后续实验设计。

板块数据确实有价值：它可以帮助判断市场是“全行业扩散上涨”还是“少数板块结构性行情”，也能在后续更好地捕捉板块切换信号。但它属于第二阶段能力，应在市场状态框架稳定后进入 v1.3。

## 1. 问题陈述

### 1.1 v1.1 已验证的问题

| 问题 | 实验证据 | 影响 |
|------|----------|------|
| **结构性牛市跑输** | 2019-2021 年策略收益 +7%，沪深 300 +36% | 最大痛点：策略在趋势明确的市场中无法捕捉行业机会 |
| **宽基模块负贡献** | 开启后收益 -11.7%（104.76% → 93.08%），回撤 +4%（-14.41% → -18.48%） | 触发条件太松（82.3% 调仓日触发），频繁追涨弱势反弹 |
| **行业信号不足** | 牛市中行业 ETF 评分 ≥ 40 的仅 2-3 只，无法填满 75% 仓位 | 入场阈值太严格（`min_total_score=40`），在趋势确认阶段就错过机会 |
| **防御填充过度** | 牛市中 30% 防御填充导致策略 beta 不足（0.42 vs 沪深 300 的 1.0） | 防御资产在强市中拖累收益，但无填充时收益腰斩（50% vs 104.76%） |
| **单维度大盘择时** | 2-state（MA50 斜率正负）过于粗糙，默认关闭反而更优 | 无法区分"牛市初期"、"牛市中期"、"牛市后期"、"震荡市"等细粒度状态 |

### 1.2 根因分析

**核心问题：行业ETF评分系统与真实市场状态脱节**

v1.1 的评分体系（趋势30 + 确认20 + 动量25 + 成交量15 + 波动率10）是基于**单只ETF的个体行为**设计的，没有考虑**板块层面的宏观信号**。这导致：

1. **结构性牛市**（如 2019-2021 科技/医药/消费）中，行业ETF本身动量不够强（横截面排名需要至少3-5只同时强势），但板块指数可能已提前数月进入趋势。
2. **宽基补仓**被设计成"行业不足时补宽基"，但触发条件（`bull_market=True` + `prev_close > MA20 * 0.98`）太松，导致在弱势反弹中频繁触发。
3. **防御填充**是双刃剑：没有填充时现金闲置（收益50%），30%填充时强市中防御占比过高（30%是慢钱），导致 beta 不足。

**结论**：第一步需要引入**市场状态（Market Regime）检测**，先把市场环境识别清楚；板块信号增强作为后续版本的输入来源和交易增强，不在 v1.2 直接落地。

## 2. 核心框架：状态 → 资产职责 → 仓位结构（用户定义）

> v1.2 的深层目标不是单纯追求 ETF 打分最高，而是建立**先识别市场状态，再决定资产职责，再决定仓位结构，最后才做 ETF 打分**的框架。

### 2.1 核心逻辑

```
市场状态识别 → 资产职责分配 → 仓位结构决定 → ETF 打分与买卖
```

这避免了模型变成纯参数拟合游戏。参数优化只能调节规则松紧，不能推翻资产职责。

### 2.2 三类市场状态与资产职责

| 市场状态 | 策略目标 | 资产职责 | 仓位结构目标 |
|----------|---------|----------|-------------|
| **大牛 / 全行业增长** | 不错过市场 beta，同时捕捉强行业 alpha | 宽基承担 beta，强行业承担 alpha，防御≈0 | 股票 > 80%，防御 < 10%，现金 < 10% |
| **震荡 / 结构行情** | 控制波动，抓行业轮动机会 | 行业轮动是主角，防御资产降低波动、承接空仓 | 股票 50-70%，防御 20-30%，现金 < 20% |
| **下行 / 风险释放** | 优先控制回撤，只保留少量反弹弹性 | 防御资产是主配置，只保留少数真正强势行业 | 股票 < 40%，防御 40-50%，现金 10-20% |

### 2.3 v1.2 分析验证：当前仓位结构问题

v1.2 observer 模式分析发现（2019-2026 全区间，按状态统计）：

| 状态 | 天数 | 股票占比 | 防御占比 | 现金占比 | 年化收益 | 夏普 |
|------|------|---------|---------|---------|---------|------|
| **强牛**（215天） | 11.9% | 65.9% | **34.1%** | 28.9% | 28.62% | 1.57 |
| **弱牛**（315天） | 17.5% | 73.1% | **24.7%** | 36.4% | 20.30% | 1.42 |
| **震荡**（297天） | 16.5% | 61.6% | 38.4% | 37.6% | 11.84% | 0.94 |
| **熊市**（826天） | 45.8% | **52.7%** | 42.3% | 43.9% | 3.88% | 0.44 |

**关键问题**：

1. **强牛阶段防御占比 34.1%** — 大牛市中，34% 仓位被防御资产占用。加上 28.9% 现金，实际股票敞口只有约 46%。这直接解释了 2019-2021 跑输 14.32%。
2. **熊市阶段股票占比 52.7%** — 熊市中股票仓位仍然过高，防御资产 42.3% 虽有效但股票敞口仍拖累。
3. **2019-2021 牛市覆盖率仅 30%** — 强牛+弱牛仅 30% 时间，70% 被判定为震荡/熊市。状态检测标准过严，或 A 股确实不是连续强牛（有多次深度回调）。

**验证结论**：市场状态框架能解释历史问题。当前问题不是状态检测本身，而是**状态与仓位结构不匹配**。后续版本需要按状态调整资产职责。

### 2.4 后续版本资产职责映射（v1.3+ 规划）

v1.2 的 4-state 可以映射到上述 3 类状态：
- 强牛 + 弱牛 → 合并为"大牛/上行"（宽基承担 beta）
- 震荡 → "震荡/结构行情"（行业轮动为主）
- 熊市 → "下行/风险释放"（防御资产为主）

| 映射后状态 | 股票仓位 | 防御仓位 | 宽基角色 | 入场门槛 | 止损 |
|-----------|---------|---------|---------|---------|------|
| 大牛 | 70-90% | 0-10% | 承担 beta（30-40%） | 降低（35分） | 放宽（-10%） |
| 震荡 | 50-70% | 20-30% | 不补仓（0%） | 默认（40分） | 默认（-8%） |
| 下行 | 20-40% | 40-50% | 不补仓（0%） | 提高（45分） | 收紧（-12%） |

## 3. 设计方案

### 3.1 市场状态检测（Market Regime Detection）

#### 3.1.1 当前问题：2-state 过于粗糙

v1.1 的 `market_timing()` 使用 `ma50_slope` 的符号（>0 或 <0）作为唯一状态：
- 正 → 满仓（100%）
- 负 → 半仓（50%）

实验验证：默认关闭（`market_timing=False`）反而更优，因为 2-state 无法区分：
- 牛市初期（MA50 刚拐头，趋势未确认）
- 牛市中期（MA50 加速向上，确认）
- 牛市后期（MA50 斜率放缓，但仍正）
- 震荡市（MA50 附近波动，无明确方向）
- 熊市初期（MA50 刚拐头向下）
- 熊市中期（MA50 加速向下）

#### 3.1.2 新方案：4-state 市场状态机

基于以下指标综合判定。v1.2 优先使用已有数据，板块数据只作为后续可替换输入：

| 指标 | 来源 | 计算方式 | 用途 |
|------|------|----------|------|
| 沪深300 相对 MA50 位置 | 收盘价 / MA50 | 高于 1.02 为强势 | 趋势方向 |
| 沪深300 相对 MA20 位置 | 收盘价 / MA20 | 高于 1.01 为短期强势 | 短期动量 |
| MA50 斜率变化 | MA50_slope(t) / MA50_slope(t-20) | 斜率加速/减速 | 趋势强度 |
| 20日波动率 | 20日收盘价标准差 / 均值 | < 0.015 为低波动，> 0.025 为高波动 | 波动率状态 |
| 市场宽度 | 现有行业ETF中收盘价 > MA50 的比例 | > 0.6 为普涨 | 市场广度 |
| 板块宽度（预留） | 申万/同花顺板块指数中收盘价 > MA50 的比例 | v1.3 接入 | 更准确判断全行业扩散 |

**状态定义**：

| 状态 | 条件 | 名称 | 仓位指导 |
|------|------|------|----------|
| 1 | 沪深300 > MA50 × 1.02 AND MA50斜率加速 AND 波动率适中 | **强牛** | 满仓（100%），防御填充降至 0% |
| 2 | 沪深300 > MA50 × 1.02 BUT MA50斜率减速 OR 波动率偏高 | **弱牛** | 满仓（100%），防御填充降至 15% |
| 3 | 沪深300 在 MA20 和 MA50 之间 OR 波动率偏低 | **震荡** | 默认（75% + 30% 填充），降低入场门槛到 35 |
| 4 | 沪深300 < MA50 × 0.98 AND MA50斜率加速向下 | **熊市** | 半仓（50%），防御填充升至 50%，提高止损到 -12% |

**状态切换规则**：
- 状态切换需要连续 5 个交易日满足条件（避免噪声）
- v1.2 先记录状态切换，不直接触发策略参数调整
- 动态参数调整只做离线模拟，稳定后再进入后续版本

#### 3.1.3 状态检测代码设计

```python
# 伪代码（待实现）
class MarketRegimeDetector:
    def __init__(self, lookback=20):
        self.lookback = lookback
        self.state_history = []
    
    def detect(self, market_df):
        """
        输入: 沪深300日K数据（含close, ma20, ma50, ma20_slope, ma50_slope）
        输出: 状态编码 (1=强牛, 2=弱牛, 3=震荡, 4=熊市)
        """
        close = market_df['close'].iloc[-1]
        ma50 = market_df['ma50'].iloc[-1]
        ma50_slope = market_df['ma50_slope'].iloc[-1]
        ma50_slope_prev = market_df['ma50_slope'].iloc[-20]
        vol_20 = market_df['close'].iloc[-20:].std() / market_df['close'].iloc[-20:].mean()
        
        # 1. 趋势位置
        trend_position = close / ma50
        # 2. 斜率变化
        slope_accel = ma50_slope / ma50_slope_prev if ma50_slope_prev != 0 else 1.0
        # 3. 波动率
        vol_regime = 'low' if vol_20 < 0.015 else 'high' if vol_20 > 0.025 else 'med'
        
        # 状态判定
        if trend_position > 1.02 and ma50_slope > 0 and slope_accel > 1.0 and vol_regime == 'med':
            new_state = 1  # 强牛
        elif trend_position > 1.02 and ma50_slope > 0 and (slope_accel <= 1.0 or vol_regime in ['high', 'low']):
            new_state = 2  # 弱牛
        elif trend_position > 0.98 and ma50_slope > -0.001:
            new_state = 3  # 震荡
        else:
            new_state = 4  # 熊市
        
        # 连续确认
        self.state_history.append(new_state)
        if len(self.state_history) > 5:
            self.state_history.pop(0)
        
        # 需要连续 5 天一致才确认
        if len(self.state_history) == 5 and len(set(self.state_history)) == 1:
            return self.state_history[0]
        return self.current_state  # 返回上一个确认状态
```

### 3.2 板块数据的角色（v1.2 预留，v1.3 实现）

板块数据可以帮助回答两个问题：

1. **状态判断**：市场是全行业扩散上涨，还是少数板块结构性上涨？
2. **板块选择**：在当前状态下，哪些板块正在切换到更强趋势？

这两件事都重要，但落地顺序不同。v1.2 先做第一件事的预留：在 `market_regime.py` 中保留 `market_breadth` 输入，默认用现有 16 只行业 ETF 计算宽度。未来 v1.3 接入申万/同花顺板块指数后，可以把 ETF 宽度替换为更完整的板块宽度。

v1.2 不做以下内容：

- 不新增 `sector_data.py` 主流程；
- 不新增 `sector_index_data` 表作为必需依赖；
- 不实现 `sector_boost_enabled=True`；
- 不让板块指数直接改变 ETF 评分或交易信号。

v1.3 再实现板块数据增强：

| 能力 | v1.2 | v1.3 |
|------|------|------|
| 用行业 ETF 计算市场宽度 | 实现 | 保留 |
| 用板块指数计算市场宽度 | 预留接口 | 实现 |
| 板块动量加成 | 不实现 | 实现 |
| 板块切换信号 | 不实现 | 实现 |
| 板块数据表 | 不强依赖 | 实现 |

### 3.3 宽基重新启用（v1.2 仅实验，不默认交易）

v1.1 已验证宽基默认开启会拖累收益：

- 宽基买入 107 次，卖出 94 次；
- 收益从 104.76% 降到 93.08%；
- 最大回撤从 -14.41% 扩大到 -18.48%；
- 夏普从 0.78 降到 0.59。

因此 v1.2 不把宽基重新启用作为默认交易目标。v1.2 只做两件事：

1. 在状态报告中标记“如果当前是强牛/弱牛，宽基是否可能适合作为 beta 补仓”；
2. 在离线实验中验证更严格条件，不影响默认策略。

后续实验的候选条件：

| 条件 | v1.1 旧值 | 后续实验值 | 理由 |
|------|----------|------------|------|
| 总评分门槛 | >= 25 | >= 35 | 避免弱信号 |
| 收盘价条件 | > MA20 * 0.98 | > MA20 | 必须真正站上均线 |
| 均线斜率 | > -0.01 | > 0.005 | 要求趋势向上 |
| 市场状态要求 | `bull_market=True` | 强牛/弱牛 | 只在牛市补 beta |
| 最小持有周期 | 无 | 14 天 | 降低频繁交易 |
| 最大宽基仓位 | 无明确限制 | 最多 1 只、20% | 保持补仓角色 |

### 3.4 动态参数调整（v1.2 离线模拟，后续默认启用）

v1.2 可以定义状态到参数的映射表，但默认不用于真实回测交易。它的用途是生成对照实验，回答：“如果未来按状态调整参数，可能改善哪些问题？”

候选映射表如下：

| 参数 | 状态 1 强牛 | 状态 2 弱牛 | 状态 3 震荡 | 状态 4 熊市 |
|------|------------|------------|------------|------------|
| `min_total_score` | 35 | 35 | 40 | 45 |
| `defense_fill_max_ratio_bull` | 0% | 15% | 30% | 50% |
| `max_position_per_etf` | 20% | 18% | 15% | 12% |
| `stop_loss` | -10% | -8% | -8% | -12% |
| `trailing_stop_mode` | standard | tiered | tiered | standard |
| `fallback_equity_enabled` | True | True | False | False |
| `fallback_equity_min_score` | 35 | 35 | 25 | 25 |
| `cooling_period_days` | 3 | 5 | 5 | 7 |

实现上先在 `config.py` 中增加 `MARKET_REGIME_CONFIG`，但设置为 observer 默认：

```python
MARKET_REGIME_CONFIG = {

    'confirmation_days': 5,  # 状态切换确认天数
    'states': {
        1: {  # 强牛
            'min_total_score': 35,
            'defense_fill_max_ratio_bull': 0.0,
            'max_position_per_etf': 0.20,
            'stop_loss': -0.10,
            'trailing_stop_mode': 'standard',
            'fallback_equity_enabled': True,
            'fallback_equity_min_score': 35,
            'cooling_period_days': 3,
        },
```

## 5. 实验计划

### 5.1 实验 1：市场状态检测准确性

**目标**：验证 4-state 检测的历史准确性

**方法**：
- 回测 2019-2026 全区间，记录每日状态
- 人工标注 2019-2021 的关键时间段（牛市初期/中期/后期）
- 对比检测状态与人工标注的混淆矩阵

**验收标准**：
- 状态切换延迟 ≤ 5 天（从真实状态变化到检测出变化）
- 强牛状态覆盖率 ≥ 60%（牛市中至少 60% 时间被检测为强牛/弱牛）
- 误报率 ≤ 20%（熊市中检测为强牛的比例）

### 5.2 实验 2：状态分布与解释性

**目标**：验证状态输出是否能解释 v1.1 的收益和回撤。

**方法**：
- 按状态统计策略日收益、回撤、持仓数量、防御资产占比。
- 输出 `reports/market_regime_summary.csv`。
- 对典型区间进行人工复盘：2019-2021、2022、2024-2026。

**验收标准**：
- 每个状态都有清晰的触发原因。
- 状态切换次数不过度频繁。
- 状态标签能够解释主要回撤阶段。

### 5.3 实验 3：observer 模式回归测试

**目标**：确认 v1.2 observer 模式不改变 v1.1 默认交易结果。

**方法**：
- 对比 v1.1 默认回测和 v1.2 observer 回测。
- 允许新增 regime 字段，但交易记录和核心绩效应保持一致。

**验收标准**：
- 总收益、最大回撤、交易次数与 v1.1 一致或差异可解释。
- `python -m py_compile` 全部通过。
- `python main.py status/backtest/signal` 可运行。

### 5.4 实验 4：动态参数离线模拟（不默认启用）

**目标**：评估状态参数映射是否值得进入后续版本。

**方法**：
- 使用状态标签生成一组实验性参数映射回测。
- 不把结果作为 v1.2 默认策略。

**验收标准**：
- 明确哪些状态参数可能有效。
- 明确哪些参数是过拟合风险。
- 为 v1.3/v1.4 提供实验依据。

### 5.5 实验 5：板块数据可用性调研（不进入交易）

**目标**：回答板块数据是否适合作为后续版本输入。

**方法**：
- 记录可获取的申万/同花顺板块指数列表、起始日期、缺失率。
- 设计 ETF 到板块指数的映射草案。
- 比较 ETF 宽度和板块指数宽度的差异。

**验收标准**：
- 明确 v1.3 是否值得接入板块指数。
- 不在 v1.2 默认回测中依赖板块数据。

### 9.2 术语表

| 术语 | 定义 |
|------|------|
| 市场状态（Market Regime） | 大盘当前所处的宏观环境（强牛/弱牛/震荡/熊市） |

| 结构性牛市 | 少数行业持续强势、多数行业平庸的市场环境（如 2019-2021 科技/医药） |
| 横截面动量 | 同一时刻所有标的之间的相对动量排名（vs 时间序列动量） |
| 等权分配 | 买入时将可用资金平均分配给所有入选标的 |

## 10. GitHub 灵感方向记录（v1.2 已探索，v1.3+ 可实施）

> 以下方向来自 GitHub 开源项目调研，v1.2 不实施，仅记录供后续版本参考。

### 10.1 ADX 指标补充（趋势强度确认）

- **来源**: [IssacWong0103/Regime-Aware-Algo-Trading](https://github.com/IssacWong0103/Regime-Aware-Algo-Trading-Python-Project)
- **核心**: ADX（Average Directional Index）衡量趋势强度，不区分方向。ADX > 25 = 趋势强，ADX < 20 = 趋势弱
- **应用场景**: 可作为 MA50 斜率的补充验证
  - MA50 斜率 > 0 + ADX > 25 → 确认强趋势（强牛）
  - MA50 斜率 > 0 + ADX < 20 → 假趋势（可能仍是震荡）
- **优先级**: P1（v1.3 可加入）

### 10.2 波动率百分位自适应（动态阈值）

- **来源**: [diaabraham/algorithmic-trading-strategy](https://github.com/diaabraham/algorithmic-trading-strategy)
- **核心**: 用历史波动率百分位代替固定阈值（0.015/0.025）
  - 波动率 < 20% 分位 → low
  - 波动率 > 80% 分位 → high
  - 中间 → med
- **应用场景**: 不同市场阶段自适应（2008 年 2% 算低，2020 年 3% 才算低）
- **优先级**: P1（v1.3 可加入）

### 10.3 Walk-Forward 验证（滚动窗口训练）

- **来源**: [Sakeeb91/market-regime-detection](https://github.com/Sakeeb91/market-regime-detection)
- **核心**: 滚动窗口训练 + 滚动窗口测试，避免过拟合
  - 训练 12 个月，测试 3 个月，窗口滚动
- **应用场景**: 验证状态检测参数是否稳定（confirmation_days=5 是否合理）
- **优先级**: P2（v1.4 或后续）

### 10.4 状态着色可视化（v1.2 已实施）

- **来源**: [tubakhxn/Market-Regime-Detection-System](https://github.com/tubakhxn/Market-Regime-Detection-System)
- **核心**: 净值曲线图上用背景色着色（绿色=牛市，红色=熊市，灰色=震荡）
- **v1.2 实现**: Plotly `add_vrect` 在 `make_nav_figure` 中加入连续 regime 段背景色
  - 强牛 = 浅红（rgba(214,79,79,0.08)）
  - 弱牛 = 浅橙（rgba(240,162,2,0.08)）
  - 震荡 = 浅蓝（rgba(91,141,184,0.08)）
  - 熊市 = 浅绿（rgba(46,157,117,0.08)）
- **状态**: ✅ v1.2 已实施

### 10.5 策略工厂模式（StrategyFactory）

- **来源**: [0x596173736972/MarketRegimeTrader](https://github.com/0x596173736972/MarketRegimeTrader)
- **核心**: 状态 → 策略自动切换
  - 牛市 → 趋势动量（Long bullish）
  - 熊市 → 均值回归（Short bearish）
  - 震荡 → 自适应波动率（Position sizing by volatility）
- **应用场景**: v1.3+ 按状态动态调整防御上限、入场门槛、宽基开关
- **优先级**: P0（v1.3 核心目标）

### 10.6 HMM / GMM 无监督状态检测（机器学习）

- **来源**: [Sakeeb91/market-regime-detection](https://github.com/Sakeeb91/market-regime-detection)
- **核心**: Hidden Markov Model 或 Gaussian Mixture Model 自动发现状态
- **优缺点**: 无需人工定义阈值，但可解释性下降（黑箱风险）
- **优先级**: P2（实验性质，不建议默认启用）
